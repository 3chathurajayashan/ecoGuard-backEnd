MODEL DETAILS & ENUM VALUES
----------------------------

  Animal
    riskStatus:   LOW | MEDIUM | HIGH | CRITICAL

  GPSCollar
    status:       ACTIVE | INACTIVE | MAINTENANCE | LOST

  RiskZone
    zoneType:     BUFFER_ZONE | HIGH_RISK_AREA | COMMUNITY_SETTLEMENT |
                  WATER_SOURCE | MIGRATION_CORRIDOR
    boundary:     GeoJSON Polygon { type: "Polygon", coordinates: [[[lon,lat],...]] }

  CommunityReport
    reportType:   ANIMAL_SIGHTING | CROP_DAMAGE | LIVESTOCK_ATTACK |
                  HUMAN_INJURY | OTHER
    status:       PENDING | UNDER_REVIEW | RESOLVED | DISMISSED

  WildlifeConflictAlert
    severity:     LOW | MEDIUM | HIGH | CRITICAL
    status:       NEW | ACKNOWLEDGED | IN_PROGRESS | CLOSED

  ResponseAction
    status:       PENDING | IN_PROGRESS | COMPLETED | CANCELLED
    syncStatus:   SYNCED | PENDING_SYNC | FAILED

  Notification
    status:       UNREAD | READ | SENT | FAILED

  User roles (existing, reused)
    RANGER | COMMUNITY_LIAISON_OFFICER | PARK_MANAGER | CONSERVATION_RESEARCHER


DESIGN DECISIONS
----------------
  1. No new FieldOfficer model created. Existing User model is reused.
     Officer assignment only accepts users with role RANGER or COMMUNITY_LIAISON_OFFICER.

  2. All routes are protected by the existing requireAuth session middleware.

  3. RiskZone boundary uses MongoDB GeoJSON + 2dsphere index.
     checkLocationInRiskZone uses $geoIntersects for accurate polygon containment.

  4. Creating a ResponseAction automatically advances a NEW or ACKNOWLEDGED alert
     to IN_PROGRESS status to reflect the real response workflow.

  5. Notification.send() is called automatically on creation, recording sentAt
     and setting status to SENT.

  6. The validate() method was renamed to validateReport() on CommunityReport
     because Mongoose reserves the name "validate" internally.


================================================================================
  SECTION 2: HOW TO RUN THE BACKEND
================================================================================

  Prerequisites:
    - Node.js v18+
    - MongoDB URI configured in .env as MONGO_URI
    - SESSION_SECRET configured in .env

  Start:
    npm start

  Expected output:
    Server running on port 5001
    MongoDB connected: <host>
    Database: ecoguard


================================================================================
  SECTION 3: POSTMAN TESTING — AUTHENTICATION FIRST
================================================================================

  All wildlife module endpoints require a valid session cookie.
  In Postman, enable "Automatically follow redirects" and keep cookies active.

  ── STEP 1: Register a test user (if not already done) ──────────────────────

  POST http://localhost:5001/api/auth/signup
  Content-Type: application/json

  {
    "firstName": "John",
    "lastName": "Ranger",
    "email": "ranger@ecoguard.com",
    "password": "password123",
    "phoneNumber": "0771234567",
    "role": "RANGER"
  }

  ── STEP 2: Register a Park Manager ─────────────────────────────────────────

  POST http://localhost:5001/api/auth/signup
  Content-Type: application/json

  {
    "firstName": "Sarah",
    "lastName": "Manager",
    "email": "manager@ecoguard.com",
    "password": "password123",
    "phoneNumber": "0779876543",
    "role": "PARK_MANAGER"
  }

  ── STEP 3: Sign in (creates session cookie) ────────────────────────────────

  POST http://localhost:5001/api/auth/signin
  Content-Type: application/json

  {
    "email": "ranger@ecoguard.com",
    "password": "password123"
  }

  Expected response:
  {
    "success": true,
    "message": "Login successful",
    "user": {
      "id": "<userId>",       <-- SAVE THIS
      "firstName": "John",
      "lastName": "Ranger",
      "email": "ranger@ecoguard.com",
      "role": "RANGER"
    }
  }

  NOTE: Save the returned user "id" — you will need it for officer assignment
        and notification recipient fields.

================================================================================
  SECTION 6: RISK ZONE ENDPOINTS
================================================================================

  IMPORTANT: GeoJSON coordinates are [longitude, latitude] (lon first)
             and the polygon ring must close (first == last point)

  ── CREATE RISK ZONE ─────────────────────────────────────────────────────────
  POST http://localhost:5001/api/risk-zones
  Content-Type: application/json

  {
    "name": "Northern Buffer Zone",
    "zoneType": "BUFFER_ZONE",
    "description": "Buffer zone along the northern park boundary",
    "boundary": {
      "type": "Polygon",
      "coordinates": [[
        [37.80, -2.50],
        [37.95, -2.50],
        [37.95, -2.60],
        [37.80, -2.60],
        [37.80, -2.50]
      ]]
    }
  }

  Expected: 201 Created
  Save the returned "_id" as <riskZoneId>

  ── CREATE A SECOND RISK ZONE ────────────────────────────────────────────────
  POST http://localhost:5001/api/risk-zones
  Content-Type: application/json

  {
    "name": "Community Settlement East",
    "zoneType": "COMMUNITY_SETTLEMENT",
    "description": "Eastern community farming area",
    "boundary": {
      "type": "Polygon",
      "coordinates": [[
        [38.10, -2.70],
        [38.25, -2.70],
        [38.25, -2.85],
        [38.10, -2.85],
        [38.10, -2.70]
      ]]
    }
  }

  ── GET ALL RISK ZONES ───────────────────────────────────────────────────────
  GET http://localhost:5001/api/risk-zones

  ── GET RISK ZONE BY ID ──────────────────────────────────────────────────────
  GET http://localhost:5001/api/risk-zones/<riskZoneId>

  ── UPDATE RISK ZONE ─────────────────────────────────────────────────────────
  PUT http://localhost:5001/api/risk-zones/<riskZoneId>
  Content-Type: application/json

  {
    "name": "Northern Buffer Zone (Updated)",
    "zoneType": "HIGH_RISK_AREA",
    "description": "Reclassified as high risk due to recent incidents"

  ── CHECK IF LOCATION IS INSIDE A RISK ZONE ──────────────────────────────────
  GET http://localhost:5001/api/risk-zones/check-location?lat=-2.55&lon=37.87

    "success": true,

  Expected:
  {
    "success": true,
    "isInsideRiskZone": false,
    "matchingZones": []

================================================================================
  SECTION 11: FULL END-TO-END WORKFLOW (Recommended Test Order)
================================================================================

  Follow this sequence to test the complete business flow in Postman:

  Step 01 — POST /api/auth/signup            (register RANGER user)
  Step 02 — POST /api/auth/signup            (register PARK_MANAGER user)
  Step 03 — POST /api/auth/signin            (sign in as RANGER — session set)
  Step 04 — POST /api/animals                (create animal EL-001)
  Step 05 — POST /api/gps-collars            (assign GPS collar to EL-001)
  Step 06 — POST /api/risk-zones             (create Northern Buffer Zone)
  Step 07 — GET  /api/risk-zones/check-location?lat=-2.55&lon=37.87
                                             (verify EL-001 location is inside zone)
  Step 08 — PATCH /api/gps-collars/:id/location
                                             (update EL-001 location)
  Step 09 — POST /api/community-reports      (community sighting report)
  Step 10 — PATCH /api/community-reports/:id/status  { "status": "UNDER_REVIEW" }
  Step 11 — POST /api/conflict-alerts        (create HIGH alert linked to report)
  Step 12 — PATCH /api/conflict-alerts/:id/acknowledge
  Step 13 — PATCH /api/conflict-alerts/:id/assign   { "officerId": "<rangerId>" }
  Step 14 — POST /api/response-actions       (ranger records action taken)
  Step 15 — PATCH /api/response-actions/:id/status  { "status": "COMPLETED" }
  Step 16 — POST /api/notifications          (notify park manager of resolution)
